# ticket-radar

**多平台余票监控与提醒框架。只读轮询、低频限流、只提醒不代下单。**

把「余票变化」这件事做成一个干净的可插拔框架：配好你要盯的车次 / 场次 / 航班，
程序按时去查，一旦余票出现就推到你微信 / 钉钉 / 企业微信 / Telegram / 邮箱，
你点链接去官方渠道自己买。

```bash
pip install -e ".[dev]"          # 想要浏览器自动登录，装 .[dev,browser]
radar init                       # 生成 tasks.yaml 和 .env.example
radar adapters                   # 看看支持哪些平台
radar check  -c tasks.yaml       # 单次查询，只打印不推送，先调通
radar status -c tasks.yaml       # 看此刻到底有没有票（--push 可发到手机）
radar run    -c tasks.yaml       # 常驻监控
radar serve  -c tasks.yaml       # 打开本地看板，看余票曲线
```

要接**猫眼 / 摩天轮**（演出票，公开接口），一条命令拿 id 就能开：

```bash
radar find maoyan 陈粒             # 搜演出，直接给出 performance_id
radar find moretickets Jay Chou    # 摩天轮用 tour_id
```

只有**大麦**需要登录态（要算 mtop 签名），多两步：

```bash
radar onboard damai              # 讲清楚 Cookie 怎么取、接口地址怎么找
radar login   damai              # 或者：开个普通浏览器让你登录，Cookie 自动写好
```

## ⚠️ 合规边界（先读这一段）

**这个项目不做抢票，这是刻意设计，不是能力不足。**

| ❌ 本仓库不做 | 原因 |
|---|---|
| 自动下单 / 自动支付 / 候补提交 | 模型层就没有这些字段，架构上表达不出来 |
| 秒级高频轮询 | 代码里硬校验 `interval_seconds >= 60`，写小了直接报错 |
| 多账号轮换、代理 IP 池 | 属于「绕过平台防御机制」，司法实践中的加重情节 |
| 验证码识别 / 设备指纹伪装 | 同上 |
| 小程序接口的加密参数逆向 | 同上。纷玩岛就卡在这一条上——它没有网页端（见下文），所以本项目接不了它 |
| 代抢牟利 | 这是被定罪的核心行为 |

**为什么把话说这么死**——2026 年的司法和监管口径已经非常明确：

- **2026-01**，四川天全县法院对一起抢购软件案宣判，8 人以**非法获取计算机信息系统数据罪**
  判处有期徒刑 3 年至 6 个月，涉案 3.27 亿元。判决书认定的核心行为是：
  绕过前端向后端发数据、避开图形验证码、伪造设备 ID、批量注册 170 余万个账号。
- **2026-04**，中央网信办与国家铁路局**联合约谈 7 家**涉火车票销售的第三方平台，明确要求
  「不得利用自动化程序实施大规模、高频次的抢票操作干扰铁路 12306 平台的安全核验措施」。
- **2026-04**，上海静安区法院对一起外挂代抢案宣判，被告人有期徒刑 1 年 6 个月（缓刑）并处罚金。
- **2025-04**，最高法 2024 年知识产权典型案例收录「抢票软件不正当竞争案」。

而且**技术上抢票也早已失效**：12306 仅 2026 年 4 月 16—18 日三天，就把 564 万笔异常交易
纳入慢速队列、拒绝出票 105.6 万张。高频请求换来的不是更快，是直接被降速。

**一句话：把间隔调小、加并发、加账号池，这个仓库就从「信息聚合器」变成上面那些案件里的
「程序」。请勿修改 `MIN_INTERVAL_SECONDS` 和相关限流逻辑。**

本项目的法律定位是**个人信息聚合工具**：查询的是公开的余票信息，只读，不改变服务端任何状态，
且只服务于使用者本人的出行决策。

## 支持的平台

| 适配器 | 平台 | 状态 | 你需要准备 |
|---|---|---|---|
| `rail12306` | 中国铁路 | ✅ **开箱可用** | 无（匿名即可，配 Cookie 更稳） |
| `amadeus` | 机票 | ✅ 需注册 | [开发者账号](https://developers.amadeus.com) 的 Key/Secret |
| `damai` | 大麦 | ⚙️ 需登录态 | Cookie（含 `_m_h5_tk`）。**只能盯项目级售票状态**（Web 端不卖票，详见「已知限制」） |
| `maoyan` | 猫眼演出 | ✅ **开箱可用** | 无（公开接口，不需要 Cookie）。只需 `performance_id`（`radar find` 拿） |
| `moretickets` | 摩天轮票务 | ✅ **开箱可用** | 无（公开接口，不需要 Cookie）。只需 `tour_id`（`radar find` 拿）。二手票，余量波动大 |
| `fenwandao` | 纷玩岛 | ❌ **没有网页端** | 接不了：票只在 App / 微信小程序里卖（见下文） |
| `json-api` | **任意返回 JSON 的接口** | ✅ 靠配置 | URL + 字段路径 |

> 猫眼和摩天轮曾经被标成「需要登录态」——那是**错的**。2026-09-30 实测：
> 两家的关键接口都是匿名的（猫眼走大众点评网关 `m.dianping.com/myshow`，
> 摩天轮走 `unify.moretickets.com`），不需要 Cookie、不需要签名。
> 现在它们各有一个真适配器，不再是「填 URL + 字段路径」的档案。

**为什么 `json-api` 还要你自己提供 URL？** 不是偷懒，是因为把接口名硬编码进代码是错的：

- 12306 的余票接口虽然无文档，但格式稳定、社区积累充分。
- 猫眼/摩天轮这类平台的接口是前端私有 XHR，**接口名、字段名随版本随时变**，
  同一平台的 App / H5 / 小程序三端还都不一样。已经实测过的两家写成了适配器，
  没实测过的平台就不该硬编码——那只会积累一堆猜出来的字段名。

所以这里的分工是：**请求、重试、解析、归一、去重写成代码；URL 和字段路径留成配置。**
接口变了改一行 YAML 就行，不用等作者发版。`radar probe` 就是为这个流程准备的——
它把接口的 JSON 结构打印成一棵树，你照着抄路径即可。

## 特性

- **七种适配器 + 一个通用兜底**：`json-api` 让「接新平台」从「写一个类」降级为
  「贴一段配置」。
- **平台级限流**：限流按**平台**生效而非按任务。配 10 个 12306 任务，对 12306 的请求
  依然被串成一个队列，不会因为「多加任务」而提高刷新频率。
- **三态余票模型**：严格区分「有票但数量未知」「0 张」「n 张」。这个区分不做对，
  状态机就会判反方向（开发过程中真的踩过这个坑，见 `tests/test_engine.py` 的回归测试）。
- **不认识的状态不猜**：平台返回看不懂的状态值时跳过该票档，宁可漏报也不误报。
  未知取值写进 debug 日志，配合 `radar probe` 排查。
- **首轮建基线**：第一轮只记录状态、不推送。否则程序一启动就刷你一屏「有票」。
- **8 个通知渠道**：ntfy / Bark / 企业微信 / 钉钉（含加签）/ PushPlus / Server酱 /
  Telegram / 邮件。默认用零注册的 ntfy，一个渠道挂了不影响其他渠道，也不影响监控本身。
- **「没配」不等于「配错」**：示例配置里开着的渠道若没填凭据，静默跳过并给一次引导提示；
  只有真配错了才报警告。所以 clone 下来不改任何配置也能直接跑。
- **指数退避**：抓取失败退避重试（30s → 1h），单任务挂掉不影响其他任务。
- **报错自带结构提示**：路径解析不出来时，直接把真实响应的 key 树打出来，
  而不是只丢一句「解析失败」。
- **密钥不进仓库**：配置里写 `${ENV_VAR}`，加载时替换。`tasks.yaml` 可以放心提交。
- **推送写明是哪天的票**：配置里写 `"+7"`，适配器会把解析后的 `2026-10-06`
  带进推送正文。同时盯多个日期时，这是唯一能把两条通知区分开的东西。
- **带票价**：`二等座　有票　¥661`。票价要按车次单独请求才拿得到，所以
  **只在确实要发通知时才补查**——常态轮询依然保持每轮 1 次请求。
- **参数变了自动重建基线**：`"+7"` 跨过午夜会指向新的一天，此时旧快照与新快照
  根本不是同一批货。程序检测到参数指纹变化就丢弃旧基准、静默重建，避免把
  「换了一天」误报成「放票了」。
- **按发车时刻筛**：`depart_after: "06:00"` + `depart_before: "12:00"` 就是「上午出发」，
  不用手抄一串车次号——车次表每天会变，写死会漏掉临时加开的车。
- **可结构化输出**：`radar check --json` 吐出带 `context` / `watched` / `matched` /
  `price` 的 JSON，方便先用脚本筛一遍再决定盯哪几趟车。
- **本地看板**：`radar serve` 在浏览器里看余票曲线，点选车次直接生成配置片段。
  曲线画成**阶梯**而不是折线——余票在两次抓取之间不会自己变，画成斜线等于
  伪造中间过程。零外部依赖（不引 CDN、不引 web 框架），断网也能用。
- **推送可预览**：`radar preview` 不用等真实放票，一条命令就能看到通知长什么样。
- **启动可报备，并且带上当前状态**：`radar run --announce` 启动时先抓一轮，
  推一条「已启动 + 每个任务现在是什么情况」。
  这个程序「安静」是常态（没变化就不推），所以需要一种方式把「在跑」和
  「没变化」区分开——不然每个人第一次用都会怀疑它挂了。
  更要紧的是：光报「活着」还不够。像大麦这种「缺货 → 热卖」才提醒的任务，
  **一开始就在卖**这件事永远等不到推送，只有把当前状态摊开才说得清。
- **随时可问**：`radar status` 抓一轮并列出各任务此刻的余票，`--push` 直接发到手机。
  和 `check` 的分工是：`check` 调配置用、只看终端；`status` 回答「现在有没有票」。
- **渠道可对比**：`radar channels` 列出每个渠道的免费额度和准备成本，并显示当前状态。
- **会自检——这是和同类脚本最大的区别。** 监控工具最危险的失败不是「抓不到」，
  而是「抓错了还报平安」。ticket-radar 在每轮抓到数据后**独立判断这一轮讲不讲得通**：
  - **语义自检**：一个平时能抠出 20 个票档的适配器，某天突然返回 0 条或全成了「未知」，
    如果只当成「这次没票」就会一直沉默——直到开场才发现监控早瞎了。自检把这种
    「解析器疑似失效」判成 `BROKEN`，**立刻推一条告警**而不是沉默。
  - **故障分级**：抓取失败不再是一句空洞的「抓取失败」，而是分成「登录态失效 /
    被平台限流 / 网络异常 / 解析失败 / 需维护者介入」五档，每档给出**下一步**。
    其中「登录态失效」是唯一用户能亲手修的——大麦 Cookie 过期那种——会**主动推告警叫人**，
    不叫，用户会以为监控还活着。
  - **健康心跳**：`radar run` 常驻时会定期推一条「我还活着 + 各任务状态」汇总，
    所以「没收到心跳」= 真的挂了，把「没变化」和「挂了」彻底分开。
    `radar health` 手动要一次同样的汇总。
- **每个需求都有归宿**——不承诺什么都能盯，但承诺**不会石沉大海**。
  每个平台都声明了自己能处理什么、做不到什么（`radar adapters` 能看到完整矩阵）。
  所以面对一个需求，它必定落到三种结局之一，而不是沉默：
  - **直接开工**：找到了能办的平台，自动建档；
  - **需要你一步**：只有需要登录的平台能办，或找到多个候选请你挑一个；
  - **做不到，但说清**：把每个平台**为什么不行**逐条列出来（例如「大麦不支持关键词
    搜索，需要你自己给场次 ID」「纷玩岛没有网页端」），而不是一句「暂不支持」。

  这条和「会自检」是同一套哲学：同类工具遇到搞不定的情况一律安静，
  而 ticket-radar 会开口解释。
- **体检不说谎：`radar doctor` 真发请求去试。**
  `radar onboard` 只看**配置**——凭据填了没有，所以它会显示「✓ 已填写」。
  可大麦那种 Cookie 只有几小时寿命，**填着也能早就失效了**。`doctor` 补的就是
  这一段：真抓一轮，真发一次探活请求，然后把结论分成五档：

  | 状态 | 含义 | 该做什么 |
  |---|---|---|
  | 正常 | 实抓成功 / 探活通过 | 不用管 |
  | **凭据问题** | Cookie 过期、Key 没填 | 跑 `radar login <平台>` 或补 `.env` |
  | 接口异常 | 连不上、结构变了 | 降频再试；别绕过平台防护 |
  | 平台不支持 | 平台层面接不了（纷玩岛） | 换个平台 |
  | **未检查** | 该适配器没实现探活 | **这不是「正常」**，用 `radar check` 实测 |

  两处刻意的设计：
  - **「未检查」不涂成绿色。** 把没查说成查过了，体检报告就成了谎报。
  - **大麦不联网就能算过期。** `_m_h5_tk` 的格式是 `{token}_{过期时间戳}`，
    读一眼就知道还剩几小时。Cookie 只有几小时寿命，如果每次体检都靠真抓去撞
    「令牌过期」，用户会频繁看到红色却什么也做不了——**告警疲劳等于没有告警**。

  代价：它会消耗平台的请求配额，所以别写进每分钟跑的 cron。
- **通知是拿在手机上看的，所以结论先行、明细有上限。**
  实测过一次同时放票 39 趟车：旧版把 39 个车次逐个列出，78 行，
  手机上「有 39 个车次有变化」这句结论**被顶出屏幕**。现在：

  ```
  **广州南 → 长沙南**
  乘车日期：2026-10-06
  **39 个车次有变化**　下面是最值得看的几个

  G1096　10:09 → 12:51
  　· 二等座　12 张　¥377　（余票出现）
  ...
  …… 还有 34 个车次有变化，跑 `radar status` 看全部
  ```

  78 行 → 26 行。排序也有讲究：**好变化在前、余票多的在前**——
  「放票」比「票变少」值得先看，同为放票则 12 张排在 1 张前面。
  全部明细随时能查（`radar status`），不塞进通知里。
- **搜到不等于找到：两道消歧 + 一次验证。**
  `radar ask "陈粒深圳场" --search` 实测踩过两个坑，都很典型：

  | 坑 | 表现 | 现在的做法 |
  |---|---|---|
  | 城市约束被丢掉 | 搜「陈粒深圳场」返回 7 条，陈粒在贵阳/三亚/广州/临沂，**一条深圳的都没有** | 城市单独提取，搜完按城市筛，并处理「广州 vs Guangzhou」中英不一致 |
  | 平台搜索是模糊匹配 | 城市筛完剩 1 条「Jordan Chan ... In Shenzhen」——**城市对、演出完全不对** | 再按演出名筛；不匹配的不删，挪进「搜到但不匹配」并说明原因 |

  选中的目标还会**用真实接口抓一次验证**：搜索索引会滞后（实测猫眼列表报
  「预售」、详情报「在售中」），而且 id 可能贴错。**搜索是「可能对」，
  验证是「确实对」。** 验证不过就明说盯不到，不给一个假的答案。
- **离线测试**：575 个测试函数（参数化展开 600+ 条）全部用 `httpx.MockTransport`，不联网、不需要账号。

## 和同类项目比，强在哪

> 一句话：**一个你能信任的余票监控——它会告诉你它自己坏没坏。**

GitHub 上做余票/回流票监控的项目不少（大麦、猫眼、纷玩岛、票星球都有人在做）。
它们能跑，但普遍缺三样东西，而这三样恰恰是「监控工具靠不靠谱」的命门：

| 维度 | 多数同类脚本 | ticket-radar |
|---|---|---|
| 技术路线 | **逆向平台签名参数**（如大麦 `sing`），能拿到票档 | **只用公开接口**，明确不逆向、不破签名 |
| 代码组织 | `Monitor_DM.py` / `Monitor_MY.py`…**每个平台一个平行脚本** | 统一适配器注册表，「一场演出 = 一趟车」语义复用 |
| 抓错了怎么办 | 四种失败（没票 / 抓不到 / 解析不了 / 被限流）**全表现为没动静** | **语义自检 + 故障分级 + 健康心跳**，详见上文「特性」 |
| 办不到的时候 | 静默。不支持就是没反应，用户以为在监控 | **逐条说明每个平台为什么不行**，并给替代方案 |
| 平台能力怎么表达 | 散落在代码里的 `if platform == ...`，加平台要改多处 | 平台自己声明 `Capability`，加平台不改路由 |
| 工程化 | 脚本级 | 575 个测试函数 + ruff + CI + Dockerfile |
| 合规风险 | 逆向签名，封号/条款风险高 | 划了明确边界（见「合规边界」） |

**为什么不做逆向签名**：那是和平台安全团队打持久战，而且从「技术对抗」滑向
「条款/法律风险」只差一步。ticket-radar 的立场是——**只监控，不抢票，不绕过**，
这个立场写在 README 第一屏，不是藏在脚注里。

**为什么加一个平台是「加一个适配器」而不是「复制一份脚本」**：平行脚本每多一个平台
就多一份需要同步维护、同步排错的代码；适配器模式让平台差异收敛到一个文件里，
公共逻辑（限流、diff、自检、推送）只写一次。面试里这能讲开，维护时也真省事。

## 架构

```
                     ┌──────────────────┐
                     │  监控任务配置      │  tasks.yaml
                     └────────┬─────────┘
                              ▼
        ┌──────────────────────────────────────────────────┐
        │  适配器层（只读 · 单账号 · 可插拔）                 │
        │  rail12306 · amadeus · damai · maoyan             │
```

### 写适配器时记得填 `Snapshot.context`

`Snapshot` 上有个 `context: dict[str, str]`，用来告诉上层「这一次查的到底是什么」。
相对日期只有适配器自己知道解析结果，所以必须由适配器填：

```python
return Snapshot(
    task_id=task.id,
    platform=self.name,
    captured_at=dt.datetime.now(dt.timezone.utc),
    context={"乘车日期": travel_date},   # "+7" -> "2026-10-06"
    trains=trains,
)
```

文案渲染会把 context 拼成一行放在标题下方（`乘车日期：2026-10-06`）。
**不填也不会报错**——只是推送里只剩「检测时间」。猫眼/摩天轮这类
没有可靠日期语义的适配器留空是合理的。

### 想加票价？实现 `enrich_prices`，别塞进 `fetch`

```python
async def enrich_prices(self, snapshot, task, client, train_codes):
    """只查 train_codes 点名的条目；查不到就原样返回，绝不抛异常。"""
```

这个钩子由 engine 在**渲染通知前**调用，而不是在轮询里。原因很直接：
12306 的票价要拿 `train_no` + 站序去另一个端点换，**一趟车一次请求**。
塞进 `fetch` 的话，54 趟车的线路每轮就会从 1 次请求变成 55 次——这个项目
的整个合规立场就是「低频只读」，不能为了一个锦上添花的字段把它破掉。

所以：常态每轮 1 次请求不变，只有真要发通知时才为命中的车次多查几次。
需要随车携带的凭据（如 `train_no`）放 `TrainState.extra`，
它不进出 diff、不落库。

补价还有**单次上限**（`engine.MAX_PRICE_LOOKUPS`，默认 10）：一场大规模放票会让
所有关注车次同时从无票变有票，不设限的话一次通知就可能打出几十个请求。
超出的车次只是没有价格，余票提醒照常发出。

>
> - 启动时带上 `--announce`，手机上会立刻收到「已启动 + 各任务当前状态」
> - 看窗口里的日志，每轮都会打一行（默认 5 分钟一轮）
> - 跑 `radar status` 问一次此刻的情况（加 `--push` 就发到手机）
> - 跑 `radar history -n 20`，看数据库里有没有在长新快照
>
> 反过来，**如果收到两条「已启动」**，说明你开了两个窗口——关掉一个，
> 否则同一条余票提醒会推两遍。
>
> **还有一种「没动静」不是故障：现在就有票。**
> 提醒规则是「变化才推」，所以一个从头到尾都有票的任务，
> 除了启动播报那一条之外不会再说任何话。演出票尤其容易撞上——
> `notify_on: [appeared]` 等的是「缺货 → 热卖」，一开始就在卖就永远等不到。
> 想知道「此刻到底能不能买」，用 `radar status --push`。

### 先看再挑：怎么决定盯哪几趟车

不确定 `watch.train_codes` 该写什么？别猜，先把数据拉下来筛一遍：

```bash
radar check --json --with-price > scan.json
```

输出里每趟车都带 `depart` / `arrive` / `duration` / 各席别余票
（`raw` 原始值、`count` 张数、`available` 是否有票、`price` 票价），
外加两样筛选用得上的：

- `context` —— 相对日期解析成了哪一天（`"+7"` → `"2026-10-06"`）
- `watched` —— **规则覆不覆盖这趟车**（时间窗 / 车次 / 席别）
- `matched` —— 覆盖，**并且**现在真的有票

典型筛法：

```bash
# 10 点前出发、二等座有余票且不超过 700 元的车次号
jq -r '[.tasks[].trains[]
        | select(.depart < "10:00")
        | select(.seats["二等座"].available)
        | select(.seats["二等座"].price < 700)
        | .train_code] | join(", ")'
```

拿到车次号回填 `watch.train_codes` 就行。顶层还有 `watched_count` / `matched_count`
两个汇总数，一条命令就能看出「盯了多少趟、其中几趟现在能买」。

三个字段值得单独说一句：

- `watched` 与 `matched` 是**两件事**，别看混：无票的车 `matched` 是 `false`，
  但它 `watched` 是 `true`——**在监控范围内**。余票监控的核心目标恰恰是「现在没票、
  等它放票」，把这两件事塞进一个字段会让人以为无票的车不会被盯，正好反了。
  想知道「这趟车会不会推给我」看 `watched`，想知道「现在就能买吗」看 `matched`。
- `matched`：光看「有票」不够，还得看**你的规则抓不抓得到**。`G3` 二等座有票、
  但 `train_codes` 里只写了 `G1`，那它永远不会推给你——只看余票很容易挑出一趟
  白高兴的车。
- `price`：**不带 `--with-price` 时是 `null` 而不是 `0`**。票价要按车次单独请求，
  所以默认不查；用 `null` 是为了让 `select(.price < 700)` 这类筛选不会把
  没查过价的票当成免费票。`--with-price` 只查命中 watch 的车次，不是全部。

### 本地看板：`radar serve`

上面那套 `check --json` + `jq` 好用，但它要求你会用命令行和 jq。「看着挑」更直接：

```bash
radar serve -c tasks.yaml
```

浏览器会自动打开 `http://127.0.0.1:8787/`，里面是三样东西：

1. **车次列表** —— 按发车时刻排序，每趟车列出各席别余票。**最近变过的值带箭头**
   （↑ 放票 / ↓ 减少），一眼看出哪趟刚动过。
2. **余票曲线** —— 点任意一行看这趟车的历史。曲线是**阶梯**不是折线：
   余票在两次抓取之间不会自己变，画成斜线等于在宣称「中间是线性变化的」。
   「有票但数量未知」画在顶部虚线上，和「0 张」严格分开。
3. **点选生成配置** —— 勾几趟车，下方直接出现可以粘进 `tasks.yaml` 的片段。

常用参数：

| 参数 | 作用 |
|---|---|
| `--port 8788` | 换端口（默认 8787，被占用时会提示） |
| `--points 500` | 曲线最多回溯多少条快照（默认 300，约 25 小时） |
| `--no-browser` | 不自动打开浏览器 |
| `--host 0.0.0.0` | 放开到局域网（**见下方警告**） |

**看板是只读的**：打开页面不会向任何平台发请求；唯一会发请求的是你点「立即扫描」。

> **安全边界**：看板默认只监听 `127.0.0.1`，且**不做鉴权**——它读的是你自己的
> 余票历史，不该默认对局域网敞开。真想让同网段的手机也能看时再加 `--host 0.0.0.0`，
> 但要清楚那意味着同一网段里的任何人都能读到你的查询配置。

**为什么曲线要做「同值压缩」**：一趟车整天都是 0 张时，300 次采样没有 300 个
信息量。后端只保留「值发生变化」的点（阶梯图在前端能完整还原），
传输量降两个数量级；但顶栏显示的采样次数仍是真实的 300 次。

### 写适配器类时：别忘了声明 capability

用 `json-api` 配置接入不需要写代码，但**手写适配器类**时必须补一段能力声明——
它是需求路由的唯一依据，漏了就等于「这个平台不接新需求」。

```python
@register("myplatform")
class MyPlatformAdapter(Adapter):
    name = "myplatform"
    requires_credentials = True

    capability = Capability(
        category="show",        # train / show / flight / generic
        summary="一句话说明这是什么平台",
        can_search=True,        # 能不能按关键词搜到具体场次
        seat_level=True,        # 能不能拿到票档级库存
        regions=("CN",),        # 覆盖地区，空元组 = 不限
        limitation="做不到什么，写具体",
    )
```

两条硬要求（都有测试盯着，漏了 `pytest` 会红）：

- **`limitation` 不许空**。它是「做不到但说清」的全部依据——空着就等于
  这个平台遇到搞不定的需求时说不出理由，又退回同类项目的沉默。
  写「拿不到票档，只能看项目级状态」，不要写「功能受限」。
- **`status="unsupported"` 要如实标**。平台层面接不了（像纷玩岛只有 App）
  就标出来，路由会直接排除它并把 `limitation` 原样显示给用户。
  别让它混在候选里，等用户配好了才报错。

声明完跑 `radar adapters` 就能在能力矩阵里看到它。

### 不想碰 F12？让浏览器替你把 Cookie 拿出来

票务平台的 Cookie 只能从登录态里来。如果「开开发者工具 → 翻 Network →
从请求头里复制 Cookie」这套让你头皮发麻，那就别自己做了：

```bash
pip install -e ".[browser]"      # 只需装一次
radar login damai                # 或者双击 login.cmd，按菜单选平台
```

会依次发生：

1. 弹出一个**普通** Edge 窗口（复用系统已装的 Edge，**不额外下载 Chromium**）
2. 你在里面正常登录 —— **这一步没有任何自动化**，所以滑块和平时一样好使
3. 把这个浏览器窗口全部关掉（或回终端按回车）
4. 程序再用一个**无头**浏览器打开同一份配置，让浏览器自己把 Cookie 交出来，写进 `.env`

写完之后会顺手体检一遍：关键字段没拿到会直接告诉你。

> **为什么登录窗口刻意不用自动化？** 因为踩过坑：阿里云的滑块能认出自动化浏览器
> （`navigator.webdriver` / CDP 痕迹），然后**无论你划得多准都判「位置不对」**。
> 正解不是把滑块划得更准——那是在骗风控，本项目明确不做设备指纹伪装——
> 而是让登录这一步**压根不沾自动化**：登录由人完成，Cookie 由浏览器自己给出，
> 程序只是不再给这件事使绊子。

几个细节：

- **登录状态会留着**：浏览器配置存在 `data/browser-profile`，
  同一个平台只需登一次；几个平台共用一个配置，各记各的会话
- **会告诉你用哪种方式登录**：例如大麦会提示「用扫码登录」——
  因为密码/短信登录中间的图形验证码最容易把人卡住，扫码则完全不出现验证码
- **不回显 Cookie 值**：终端只报条数和字段名，值不会出现在屏幕上或日志里
- **全程本地**：不经过任何第三方服务，登录态不出这台机器
- **想找接口地址**：登录后跑 `radar sniff <演出页地址>`，它用刚存下的登录态
  打开页面，把调用的数据接口列出来（登录期间程序看不到网络请求了，
  所以这一步拆成了独立命令）

> **为什么不直接读你日常浏览器的 Cookie 数据库？** 两层原因：
> 一是 Edge / Chrome 近年上了**应用绑定加密**（`Local State` 里同时有 `DPAPI`
> 和 `APPB` 两套密钥，新 Cookie 走后者），离线解不开；
> 二是那是**你整个浏览器**的数据，本项目只该碰自己这个 profile。
> 用独立的配置启动一个浏览器，是既干净又正当的做法。

> `radar login --automated` 是留给「平台没有风控」场景的逃生门。
> 默认别用——撞上滑块就说明该去掉这个参数。

#### 双击 `login.cmd` 一闪而过？

先别怀疑代码。这种「黑窗开了又没了」的闪退，绝大多数不是 Python 的问题，
而是**换行符**的问题：

`.cmd` / `.bat` 是给 Windows 的 cmd.exe 读的，必须用 **CRLF** 换行。
可这类文件一旦被某些编辑器或脚本工具改过，很容易变成 Unix 的 **LF**。
cmd.exe 读到 `if (...)` 这种**跨行块**时就会解析出错，直接终止整个批处理——
连文件末尾那句 `pause` 都来不及执行，于是窗口一闪就关了。
`cd /d "%~dp0"`、`set /p`、多行 `if` 块这几个地方对这种格式最敏感。

所以本项目里三个启动脚本（`login.cmd` / `run-monitor.cmd` / `onboard.cmd`）
都按 **CRLF + GBK** 保存——GBK 是为了让中文提示在 cmd 的 936 代码页下
不乱码。每个脚本还会在**自己旁边**写一份日志：

- `login.cmd` → `login.log`
- `run-monitor.cmd` → `monitor.log`
- `onboard.cmd` → `onboard.log`

排查口径很简单：

- 日志里**只有「启动」没有「结束」** → 脚本在**解析阶段**就崩了，是换行符
  或编码问题，跟 Python 无关（脚本本身没跑起来）
- 日志里**两者都有** → 脚本跑完了，问题在 Python 那一侧，看退出码

想看当场报错就别双击：在文件管理器地址栏敲 `cmd` 回车，
在弹出的窗口里输入 `login.cmd`——这回报错会留在屏幕上，不会跟着窗口一起消失。

另外脚本现在还会先自检：找不到 `python.exe` 或 `tasks.yaml` 时，
它会**把具体路径打出来**再停下，而不是默默闪退。

### 演出票平台：抓 Cookie 的准确步骤

三家演出票平台里，**只有大麦需要登录态**（它要算 mtop 签名）。猫眼和摩天轮的
接口是公开的，一个 Cookie 都不用——直接 `radar find` 拿 id 就能跑。

下面以**大麦**为例，讲需要登录态时的那套手工流程。

> 想手工做、但不想自己摸索？跑 `radar onboard damai`（纷玩岛换成 `fenwandao`，
> 也认中文名）。它按平台把步骤打出来，并顺手检查 `.env` 里那条
> Cookie 填对了没——只报长度，不回显内容。

1. 浏览器打开 <https://www.damai.cn> 并**登录**
   —— 登录框上方**切到「扫码登录」**，手机打开大麦 App（或淘宝 App）扫一下即可。
   走「密码登录 / 短信登录」中间会弹**图形验证码**，而且经常反复失败；
   扫码全程不出现验证码。本项目**不破解验证码**，换一种登录方式是唯一正解。
2. 打开你要盯的那场演出的详情页，确认页面上能看到场次和票档
3. 按 `F12` → 切到 **Network**（网络）标签 → 按 `F5` 刷新页面
4. 在请求列表里点第一条（通常是页面本身）
5. 右侧找 **Request Headers** → 找到 **Cookie** 那一行 → 右键 → **Copy value**
6. 演出 ID 在地址栏里：`https://detail.damai.cn/item.htm?id=8xxxxxx` 中 `id=` 后面那串数字

整条 Cookie 原样丢进 `.env` 即可，程序只从里面读它需要的字段：

```bash
DAMAI_COOKIE=_m_h5_tk=xxx_1699999999999; _m_h5_tk_enc=yyy; ...
```

三家分别对应 `.env` 里的 `DAMAI_COOKIE` / `MAOYAN_COOKIE` / `MORETICKETS_COOKIE`。

> **后面那两条现在是可选的。** 猫眼和摩天轮不需要 Cookie；`MAOYAN_COOKIE` /
> `MORETICKETS_COOKIE` 留着只是「填了也会带上」。别为了它们去折腾 F12。

> **Cookie 会过期**（一般十几天到几十天）。过期后的表现是响应里带
> `FAIL_SYS_TOKEN_EXPIRED`，照着上面复制一条新的就行。程序**不会**代你登录、
> 不会处理验证码、也不会做小程序接口的签名逆向——遇到风控请降低频率或稍后再试。

### 纷玩岛：接不了——不是没做，是它没有网页端

这个结论是实地查证出来的（2026-09），写在这里省得以后有人再白试一遍：

- `www.fenwandao.com`（各应用商店标注的官网）**HTTPS 证书域名不匹配、HTTP 直接连接重置**，
  浏览器和 curl 都打不开；
- 它的真实域名是 `livelab.com.cn`，主体为**上海名辉文化发展有限公司**（包名 `cn.com.livelab`）。
  能打开的 `m.livelab.com.cn` 是个**静态 App 下载落地页**——页脚还写着「纷玩岛 © 2021」，
  点「演唱会」页面纹丝不动，**一个 xhr 请求都不发**；
- 也就是说纷玩岛的票只在 **App 和微信小程序**里卖。小程序接口带 `wx` 系签名参数，
  浏览器里拿不到可复用的地址——而这正是上文合规边界里的红线之一。

**所以 `radar login fenwandao` 会直接拒绝你，并说明原因；`radar onboard fenwandao`
会讲清楚来龙去脉。** 适配器代码仍保留在 `radar/adapters/shows.py`，
它哪天上了网页版票务页，用 `radar probe` 探一下就能直接接上，不用重写。

想盯演出票，有三条腿（详见下文「已知限制」）：

- **猫眼 / 摩天轮**：公开接口，`radar find` 拿 id 就能开，不用登录；
- **大麦**：需要登录态（`radar login damai`），只能盯项目级售票状态。

「现在到底能不能买」用 **`radar status --push`** 随时问一次，比干等推送实在。
但大麦有个必须说清的边界：**它的 PC 网页端已经不卖票了**（详情页按钮恒为
「该渠道不支持购票」），票档余量只存在于 App 的选座页。所以本工具对大麦盯的是
**项目级售票状态**（热卖 / 缺货 / 预约）——粒度比票档粗，但足以回答
「现在到底能不能买」。详见下文「已知限制」。

### 懒得数下标？让 AI 来（可选）

`radar probe` 能打出结构树，但「哪个字段才是余量」仍要自己判断。
如果你有任意 OpenAI 兼容的网关（B.AI / 自建 vLLM 都行），可以让它代劳：

```bash
# 1. 先把响应存下来
radar probe "https://api.example.com/items/12345/tickets" \
  --cookie-env MY_COOKIE --save raw.json

# 2. 让它推断字段路径
radar infer raw.json --intent "各大票档的余量" \
  --url "https://api.example.com/items/12345/tickets"
```

输出是一段可以直接合并进 `tasks.yaml` 的 `params`：

```yaml
params:
  items_path: data.performances
  item_id: [performId]
  item_label: [performName]
  seats_path: seatPlanList
  seat_name: [seatName]
  seat_status: [seatStatus, remainNum]
```

关键在于：**这段配置在交给你之前，已经被真实解析器试运行过了。**
模型给的路径如果解不出单元或票档，会被当场退回、带着失败原因重试一次；
两次都不行就明确报失败，而不是让你拿着一份「看起来对、跑起来空」的配置。

配置方式（写进 `.env`）：

```ini
LLM_BASE_URL=https://api.b.ai/v1   # 任何 OpenAI 兼容网关
LLM_API_KEY=sk-...
LLM_MODEL=deepseek-v4-flash
```

> 这是**开发期**工具，不是运行期依赖。不配这三个变量，监控本身照常运行——
> 抓取、限流、去重、推送全是本地确定性逻辑，离线可测。
> `radar models` 可以列出网关上的可用模型名，省得靠猜。

## 配置

完整示例见 `tasks.example.yaml`（含全部七个平台的示范任务）。最小可用配置：

```yaml
storage:
  path: ./data/radar.db

notify:
  - type: ntfy                      # 零注册：装个 App，订阅下面这个名字即可
    options:
      topic: ${NTFY_TOPIC}          # 换成一段随机串，别用 ticket 这种

tasks:
  - id: jinghu-morning
    adapter: rail12306
    interval_seconds: 300        # 低于 60 会被拒绝加载
    link: https://www.12306.cn/index/
    params:
      date: "+7"                 # 支持 YYYY-MM-DD / today / tomorrow / +N
                                 # 相对日期跨零点会指向新的一天，届时自动重建基线
      from: 北京南
      to: 上海虹桥
    watch:
      seat_types: ["二等座", "一等座"]
      min_count: 1
      train_codes: ["G1", "G3"]
      depart_after: "06:00"      # 只看上午发车的：区间 [06:00, 12:00)
      depart_before: "12:00"
      notify_on: ["appeared"]    # 默认只推「余票出现」
```

`notify_on` 可选值：`appeared`（无票→有票）、`increased`、`decreased`、
`sold_out`、`new_train`（加开车次 / 加开场次）。默认只推 `appeared`，避免噪声。

#### 按发车时刻筛，而不是列车次号

想表达「我只关心上午出发的车」，用 `depart_after` / `depart_before`，
别去数车次号：

```yaml
depart_after: "06:00"     # 含 06:00
depart_before: "12:00"    # 不含 12:00
```

区间是**左闭右开** `[06:00, 12:00)`，所以「上午」直接写 06:00 ~ 12:00 就行，
不用纠结 12:00 整算不算上午。两个理由值得这么做：

- **车次表每天会变**。写死 `train_codes` 会漏掉临时加开的车，
  而那往往正是会放票的那趟。同一段线路动辄 50 趟车，手抄一遍既容易错也没意义。
- **约束要写在真正想表达的地方**。「上午出发」是时间，不是一串车次号。

边界行为：

- 时刻必须写成 `HH:MM`，`6:00` 会被自动归一化成 `06:00`。
  时间窗内部靠**字符串比较**实现（`'06:00' <= '10:30' < '12:00'`），
  这只有在零填充时才成立——`'6:00' > '10:30'`，一个没补零的写法就能让上午的车
  全部漏掉且不报错。所以一律先归一化，不留踩坑的机会。
- 拿不到发车时刻时**放行**。时间窗是给 12306 这类有时刻概念的数据用的；
  演出票、二手票适配器给不出发车时刻，卡死只会让监控静默失效——
  宁可真推多了，也不要一条都不响。

#### 相对日期的注意事项

`date: "+7"` 是**相对今天**解析的，过了午夜就指向新的一天。程序会给每轮快照
打一个 `params` 指纹，**指纹一变就丢弃旧基准、本轮只重建基线、不推送**——
否则拿 10-07 的余票去比 10-06 的余票，会把「换了一天」误报成「放票了」。

代价是：如果你用 `+7` 这种滚动日期，每天跨零点的第一轮是静默的（日志里会有
一行「任务参数已变化，快照基准不可比」）。想连续监控同一天的票（例如抢某场演出
的开票），把日期写成绝对日期 `2026-10-06` 就不会触发重建。

## 通知渠道

先跑一次 `radar channels`：它会列出全部渠道的免费额度和准备成本，
并显示你当前配到了哪一步。

本项目是开源的，所以**默认渠道不能建在作者的付费墙上**。
按这个标准，渠道分三档：

| 渠道 | 免费额度 | 直达微信 | 你要准备什么 | 可自建 |
|---|---|---|---|---|
| **ntfy** ⭐ | 250 条/天 | ✗ | 一个猜不到的 topic 名 | ✅ |
| **bark** | 免费 | ✗ | Bark App（仅 iOS） | ✅ |
| wecom | 20 条/分钟 | ✗ | 建个只有自己的企微群 | ✗ |
| dingtalk | 20 条/分钟 | ✗ | 建个钉钉群 + 机器人 | ✗ |
| pushplus | 200 条/天 | ✅ | 扫码 + **实名认证** | ✗ |
| serverchan | **仅 5 条/天** | ✅ | 扫码 | ✗ |
| telegram | 免费 | ✗ | 自备网络环境 | ✗ |
| smtp | 看邮箱 | ✗ | 邮箱授权码 | ✗ |

### 为什么默认是 ntfy

ntfy 是唯一**不需要注册任何账号**的渠道：装个 App，订阅一个名字，就完了。
它本身是开源项目（Apache-2.0 / GPLv2），官方公共实例免费 250 条/天；
嫌不够或者在意隐私，一行 Docker 就能自建：

```bash
docker run -d -p 8080:80 binwiederhier/ntfy serve
```

自建后在 `tasks.yaml` 的 ntfy 段加一行 `server: https://你的域名` 即可。

**唯一要注意的**：ntfy 的 topic 名就是密码。任何人猜到这个名字都能收到你的通知，
所以别用 `ticket` 这种，用一段随机串：

```bash
python -c "import secrets;print('ntfy-radar-'+secrets.token_hex(6))"
```

iOS 用户可以考虑 `bark`——它走苹果 APNs，比 ntfy 更即时，
还支持「重要警告」穿透勿扰模式，抢时间的场景很实用。

### 想直达微信怎么办

`pushplus` 最省事（实名后 200 条/天），但**必须实名**，而且免费额度由平台说了算——
这类聚合服务改政策的先例不少，所以它没进默认配置。`serverchan` 免费版每天只有 5 条，
做余票监控基本不够用。

如果只是想要「手机响一声」，`wecom`（企业微信）和 `dingtalk` 更稳：
建个只有自己的群、加个机器人，永久免费、额度宽松，
缺点是消息落在群里而不是私聊。

> 没配任何渠道也能跑：余票变化照常写进本地数据库，只是不推送。
> 想先观察一段时间，用 `radar run --no-notify` 就行。

## 已知限制

- **12306 字段下标会漂移**。余票接口没有官方文档，字段位置靠社区逆向。
  代码里所有取值都做了越界保护，字段缺失只会让该席别消失、不会崩。
  真的漂移了就用 `radar debug-raw` 看真实下标，然后在 tasks 的
  `params.train_fields` / `params.seat_fields` 里覆盖，**不必改代码**。
- **演出票平台分成两种，别混着说**（2026-09-30 实测）：
  **猫眼和摩天轮的接口是公开的**——不需要 Cookie、不需要签名，各自有真适配器，
  `radar find` 拿 id 就能跑；**只有大麦需要登录态**（要算 mtop 签名），
  且它的接口名 / appKey 会漂移。对没实测过的平台，仍然只用 `json-api`
  配 URL + 字段路径，不硬编码猜出来的字段名。
- **猫眼的状态有两个来源，列表那份是旧的**。同一时刻搜索接口报「预售」、
  详情接口报「在售中」——列表读的是搜索索引，详情才是权威。
  适配器只信详情，**即使配的是关键词也会多请求一次详情**。多这一次是值得的，
  读旧状态会让整条提醒链失效（该响不响）。
- **猫眼 `ticketStatus` 是数字码，有官方词表**：1 即将开售 / 2 预售 / 3 在售中 /
  4 已售罄 / 5 已结束 / 11 即将预售 / 12 演出延期（从站点 JS 里挖出来的原文）。
  看不懂的值**不猜**、直接报错并打印已知映射。注意「即将开售」被划进「买不到」——
  这样它开售那一刻正好产生一次 `appeared`，那才是你真正想收到的那条。
- **摩天轮只认 POST**。同一个地址用 GET 会返回一个 111 字节的空壳
  （`statusCode: 12123`）——那是「请求姿势不对」，不是平台故障，别被它带偏。
- **摩天轮的城市字段有两层**：`regionName` 才是真实城市（`Guangzhou, CN`），
  `cityName` 是国家/地区级（`China`）。适配器用前者做场次键和城市过滤——
  用后者会让整个中国巡演挤在一个 `China` 下面，场次互相覆盖。
- **摩天轮的价格是挂单价，且带币种**。境外场次返回的是**港币（`HK$`）**，
  不是人民币；模型里的 `currency` 字段就是为这个加的——把 3499 港币渲染成
  「¥3499」等于报了一个错误的价格。价格含卖家溢价，可能高于票面，自行判断。
- **摩天轮的搜索很松**：搜「周杰伦」会连带返回 ENHYPEN、Blue 等不相干的场次。
  别照搜索结果第一行随便填，用 `radar find` 挑准 `tour_id`。
- **摩天轮是二手票平台**，所以「某站没挂单」是常态不是故障，冷门演出可能整站都没有。
  建议 `notify_on` 只留 `appeared`，并把 `min_count` 调高一些，否则通知会很吵。
- **大麦的 Cookie 会失效**（通常几十天）。届时抓取会报错并把响应结构打出来，
  回浏览器换一条即可。猫眼/摩天轮没有这个问题——它们不用 Cookie。
- **大麦 Web 端不卖票，所以别指望在网页里看到「立即购买」**。2026-09-30 实测：
  PC 详情页的 `buyButton.text` 恒为「该渠道不支持购票」、`tip` 是「请到大麦App购买」；
  详情页的 xhr/fetch 响应体里一个票档关键字都没有（页面上那些「缺货」字样
  来自前端 JS 文案）。**这不是本工具的限制，是大麦的产品设计。**
- **因此对大麦盯的是「项目级售票状态」**：接口
  `mtop.damai.item.detail.getdetail` 返回的
  `data.guide.tour.projectList[].saleStatus`（热卖 / 缺货 / 预约）。
  粒度比票档粗，但足以回答「现在到底能不能买」——回流票场景要的就是这个。
  配 `params.city` 可只盯巡演其中一站（如 `city: 广州`）。
- **多日期共用同一个项目状态**：一场演出的多个日期，只要还有任一场可购就是「热卖」。
  所以盯加场时，主场的售罄不会让它变「缺货」，要两场都卖光才会变——
  刻意保守：宁可漏报，也不误报。反过来说，
  **看到「热卖」不等于你想蹲的那一场还有票**，具体场次要去 App 确认。
- **「热卖」期间不会有任何推送，这不是漏接平台**：提醒规则基于**变化**，
  「一直都在卖」不构成变化。`notify_on: [appeared]` 等的是「缺货 → 热卖」那一刻，
  它要是一开始就在卖，那就永远等不到——除了启动播报，手机上不会再有大麦消息。
  想知道此刻到底能不能买，用 `radar status --push`。
- **换成 App 端的 api 名，也拿不到票档**（2026-09-30 实测）。用 Web 端签名请求
  App 在用的 `mtop.alibaba.damai.detail.getdetail`，网关回 `SUCCESS::调用成功`，
  业务层却回一句 `对不起，小二很忙，请稍后再试`——这是**风控软拒绝**：
  签名是合法的，但它认得出这不是 App 发出来的请求（缺设备指纹与 App 专属请求头）。
  要拿到票档，只能复刻 App 那整套签名链（`libmtguard.so` / `libsgmain.so`，
  社区通行做法是 frida hook `NativeSecurityGuard.getSign` + 伪造
  `x-mini-wua` / `x-sgext` / 设备指纹）。那已经不是在「读数据」，
  而是在「对抗风控」，**本项目到此为止，不做**。
- **所以热门演出的票档余量，本工具永远拿不到，也不打算拿。**
  而且对热门场次，那个数字本身价值也有限——票是秒没的，
  5 分钟一轮的监控看到的余量早就过期。真正有效的是大麦 App 官方的
  **「缺货登记 / 回流票开售提醒」**：官方直连，比任何第三方监控都快。
  本工具负责的是「项目级状态」和「开售/回流那一刻的通知」，抢的活交给官方。
- **大麦的接口名与 appKey 都会漂移**，两者都是 `params` 可覆盖的配置项。
  2026-09-30 实测有效的是 `mtop.damai.item.detail.getdetail` 配 `appKey=12574478`（H5 端）；
  旧的 `mtop.damai.wireless.project.getprojectdetail` 与 `appKey=23739456` 均已失效
  （前者返回 `FAIL_SYS_API_NOT_FOUNDED`，后者签名不匹配）。改配置即可，不必改代码。
- **详情页 SSR 里的内嵌 JSON 仍可匿名读**（含 `performBases`、`priceRange`、
  `sellStartTime`），但那是静态信息、不含余量，只适合做「开售时间到了没」这类判断。
- **大麦的登录态横跨多个域**：`.damai.cn` 放 `_m_h5_tk`，`ipassport.damai.cn`
  （登录子域）另放一组，阿里系又在 `.mmstat.com` / `.ynuf.aliapp.org`。
  `radar login` 按「同一站点 + 阿里系」收集，实测 17 条；
  只问主域会漏掉登录域那几条。
- **只支持单机单进程**。没有分布式协调，因为一个低频只读的监控器不需要。

- [x] 12306 铁路余票适配器
- [x] 机票走 Amadeus 正规开放 API
- [x] 大麦（含 mtop 签名）/ 猫眼 / 摩天轮
- [x] 猫眼与摩天轮改成真适配器 —— 实测它们的接口是**公开**的，不需要登录态
- [x] `radar find`：把演出名翻译成平台内部 id（`performance_id` / `tour_id`），不用碰 F12
- [ ] 纷玩岛 —— 等它出网页版；目前只有 App 和小程序，浏览器盯不了（见上文）
- [x] 通用 `json-api` 适配器 + `radar probe` 结构探查工具
- [x] 会自检：**语义自检 + 故障分级 + 健康心跳**——抓错了会主动叫你，而不是沉默（见「特性」）
- [x] **能力声明层**：每个平台声明能处理什么 / 做不到什么，路由据此分派需求（见「特性」）
- [x] **`radar doctor` 真发请求体检**：`onboard` 只看配置填没填，`doctor` 管「还能不能用」，
      五档结论且「未检查」不冒充「正常」
- [x] **意图解析**：`radar ask` 把一句话 / 一条链接翻成结构化需求。**纯规则、不联网、不用 LLM**——
      解析不了会明说，判不出类别就把所有可用平台列出来让你挑，而不是一律拒绝
- [x] **目标解析**：`radar ask --search` 搜平台 → **按城市 + 演出名双重消歧** → 用真实接口
      **验证一次** → 输出可直接粘贴的 YAML。搜到但不对的会列出来并说明哪里不对，**宁可不许给错**
- [ ] `radar watch`：把 ask + 定位 + 写配置 + 启动合成一条命令（粘贴即监控的最后一公里）
- [x] 本地 Web 看板（`radar serve`）：余票阶梯图 + 点选车次生成配置
- [x] 接入引导（`radar onboard`）：按平台打印取 Cookie / 找接口的步骤，并体检凭据
- [ ] 教务系统（成绩 / 课表 / 选课余量）
      —— 它和票务平台是同一个问题：带登录态查一个私有接口，适配器 / 状态机 /
      通知渠道都能直接复用。但**需要新写一个「登录 + 会话刷新」适配器**：
      登录走统一身份认证、Cookie 会过期、部分系统的数据是 HTML 表格而非 JSON。
      明确不做抢课：那会自动提交表单，性质是「代你操作」而不是「只读提醒」。
- [ ] 公众号 / 微信小程序前端
      —— 注意：**个人主体做不了票务类目**，提交会被驳回，需要企业主体。
      所以第一版先做 CLI + 本地看板，小程序等有主体了再说。
